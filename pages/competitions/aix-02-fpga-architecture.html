2. YOLOv2 전체 계산을 FPGA 안에서 이어 가기

객체검출 모델은 convolution 연산기 하나만으로 완성되지 않습니다. YOLOv2에는 feature map의 크기를 바꾸는 pooling과 upsample, 앞선 결과를 다시 가져오는 route, 서로 다른 크기의 물체를 찾는 두 detection head가 있습니다. 이 글에서는 22개 처리 단계가 FPGA와 DDR 안에서 끊기지 않고 실행되는 구조를 설명합니다.

Full-graph execution
Convolution만 가속하는 것이 아니라 Pool, Route, Upsample과 두 detection head까지 모델 전체를 FPGA에서 계산합니다.
Descriptor scheduling
각 단계의 연산 종류, tensor 크기와 DDR 주소를 ROM에 기록하고 scheduler가 순서대로 읽어 실행합니다.
DDR workspace
입력, weights, 중간 feature map과 두 head 출력을 충돌하지 않는 주소 영역에 배치한 공용 작업 공간입니다.
Data reuse·prefetch
같은 feature와 weight를 다시 쓰고 다음 데이터를 미리 가져와 MAC이 DDR 응답을 기다리는 시간을 줄입니다.
Backpressure
다음 단계가 데이터를 받을 수 없을 때 valid/ready 흐름으로 앞단 연산을 안전하게 멈추는 제어입니다.

Python host는 bitstream을 올리고, 정수 weights와 입력을 DDR에 기록한 뒤 실행을 시작합니다. FPGA는 DDR에서 필요한 데이터를 읽어 각 layer를 계산하고, 8×8과 16×16 크기의 두 detection head를 다시 DDR에 남깁니다. host는 두 결과를 읽어 bounding box를 해석하고 NMS와 정확도 평가를 수행합니다.

데이터 이동에는 JTAG-to-AXI를 사용했습니다. UART 115200bps로 큰 tensor를 옮기면 계산 시간보다 전송 시간이 훨씬 길어지기 때문에, DDR와 제어 레지스터에 직접 접근해 FPGA 계산과 통신 시간을 구분했습니다.

Route·Upsample과 두 detection head를 포함한 비선형 그래프

앞부분의 convolution과 pooling은 이미지에서 점점 복잡한 특징을 추출합니다. 중간의 첫 detection head는 비교적 작은 8×8 feature map을 사용합니다. 다른 경로에서는 앞선 feature map을 upsample한 뒤 route로 가져온 값과 합쳐 16×16 detection head를 계산합니다. 이 우회 경로가 있어 작은 물체와 큰 물체를 서로 다른 해상도에서 찾을 수 있습니다.

22개 descriptor를 다섯 구간으로 읽기

22라는 숫자는 convolution이 22개라는 뜻이 아닙니다. descriptor index 0–21에 Conv, Pool, Route, Upsample과 두 detection 단계가 함께 들어 있습니다. 전체 흐름은 아래 다섯 구간으로 정리할 수 있습니다.

Descriptor ROM이 제어하는 22개 처리 단계

FPGA 안의 descriptor ROM은 각 단계의 연산 종류, 입력과 출력 크기, kernel, stride, padding과 DDR 주소를 보관합니다. scheduler는 현재 번호의 descriptor를 읽어 Conv, Pool, Route, Upsample 또는 Detection 경로를 선택합니다. 덕분에 host가 layer마다 크기와 주소를 다시 보내지 않아도 모델 순서가 FPGA 안에서 이어집니다.

3×3과 1×1 연산에 재사용되는 144-lane INT8 MAC

convolution의 핵심은 입력과 weight를 곱해 더하는 MAC 연산입니다. 144는 임의의 병렬도 숫자가 아니라 3×3×16입니다. 3×3 kernel의 16-channel 묶음 하나를 한 번에 처리하면 한 출력 위치의 144개 곱셈 항이 만들어집니다. 입력 channel이 16보다 큰 layer는 16-channel chunk를 반복하고 INT32 accumulator에 이어서 더합니다.

각 lane은 같은 signed INT8 weight와 두 위치의 activation을 한 DSP 곱셈에 packing합니다. 정상 3×3 경로에서는 한 번 받아들인 cycle마다 두 개의 144-term spatial dot product를 파이프라인으로 계산합니다. 1×1 경로에서는 144개를 그대로 두지 않고 32-lane group 네 개로 나눠, 2×2 위치와 네 output channel을 처리한 뒤 결과를 순서대로 내보냅니다. 별도의 1×1 전용 MAC array를 추가하지 않은 이유입니다.

이론 peak와 11.42 FPS의 차이 28.8G는 packed lane이 모두 유효한 3×3 구간의 구조적 상한입니다. 모델 전체에서는 channel chunk 반복, 1×1 lane 배치, DDR read/write, descriptor 전환, Pool·Route·Upsample, requantization과 backpressure가 포함됩니다. 따라서 이 값으로 전체 FPS를 직접 계산하거나 실제 지속 처리량으로 표현하지 않습니다. 최종 DSP 205개에는 144개 MAC lane 외에 requantization과 주변 산술도 포함됩니다.

MAC 처리량을 제한한 DDR·cache·write-back 병목

MAC이 많아도 필요한 feature map과 weight가 제때 도착하지 않으면 연산기는 기다립니다. 반대로 계산이 끝나도 DDR 쓰기 경로가 막히면 다음 layer로 넘어갈 수 없습니다. 그래서 성능 개선은 연산 수뿐 아니라 데이터 재사용, prefetch, burst 전송과 valid/ready 흐름을 함께 봤습니다.

최종 detector 정확도에 필요한 CONV14·CONV20 두 head

개발 중에는 16×16 CONV20 경로만 실행해 연산 속도를 확인할 수 있습니다. 그러나 이는 전체 detector가 아닙니다. 8×8 CONV14와 16×16 CONV20이 서로 다른 크기의 물체를 담당하므로, 최종 정확도는 두 출력을 모두 저장하고 함께 후처리한 build에서 평가해야 합니다. 다음 글의 최종 수치도 이 full-graph 조건에서 얻은 결과만 사용합니다.

이 단계에서 한 일

정수 layer가 개별적으로 맞는 상태에서 끝내지 않고, descriptor와 DDR offset을 기준으로 22단계 실행 경로를 연결했습니다. 통합 과정에서는 layer별 readback으로 최초 mismatch 지점을 찾고, weight cache, feature 재사용, burst 전송과 write backpressure를 조정했습니다. 최종 detector가 두 head를 모두 남기도록 실행·저장 경로를 확인했습니다.
