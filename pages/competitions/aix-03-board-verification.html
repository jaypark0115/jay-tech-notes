3. 한 장의 동작 확인을 229장 detector 평가로 확장하기

첫 이미지는 주소와 실행 순서를 빠르게 점검하는 데 유용하지만, 가속기의 정확도와 안정성을 대표하지는 않습니다. 그래서 test_one으로 전체 경로를 확인한 뒤, 같은 bitstream과 weight로 229장을 연속 실행하고 두 detection head의 출력까지 detector mAP로 평가했습니다.

검증의 기준

FPGA가 done 신호를 냈는지, 두 head가 모두 읽혔는지, cycle 수가 정상인지, 그리고 출력이 실제 box·class 평가에서 정확도를 유지하는지를 단계별로 확인했습니다. 중간 개발 단계의 최고 FPS는 최종 성과에서 제외하고 229장 최종 실행값만 사용했습니다.

bitstream program, DDR input/weight preload, start와 done, CONV14·CONV20 readback, 후처리까지 한 번에 확인합니다.

test_all

program과 weight preload는 한 번만 수행하고 입력 이미지만 바꿔 229장을 처리해 반복 실행 안정성을 확인합니다.

11.420687 FPS는 FPGA 계산 구간만 측정한 값입니다

100MHz cycle counter에서 한 이미지의 평균은 8,756,040 cycles, 87.560404ms였습니다. 이를 역수로 계산한 값이 11.420687 FPS입니다. JTAG 입력 전송, Python 전처리와 detector 후처리는 이 수치에 포함하지 않았습니다.

측정 구간확인값포함 범위
FPGA cycle counter87.560404ms · 11.420687 FPS가속기 compute-only
229장 JTAG session1,807.586sProgram, preload, readback, 평가와 고정 overhead

JTAG은 검증 인터페이스이므로 전체 세션 시간을 실시간 카메라 처리량으로 해석하지 않습니다. 반대로 compute-only FPS에도 데이터 전송과 후처리가 없다는 경계를 함께 표시합니다.

최종 critical path는 MAC 산술 자체가 아니라 weight cache write-side register에서 BRAM 입력으로 이어지는 route에 있었습니다. 연산기만 파이프라인화해도 timing 문제가 끝나지 않고, cache 배치와 routing까지 함께 봐야 한다는 결과입니다.

최초 mismatch가 생긴 layer부터 추적했습니다

데이터 형식

Packing과 signedness 확인

HWC byte 순서, signed/unsigned activation과 head output 범위를 software reference와 맞췄습니다.

주소

Descriptor와 DDR offset 확인

Route의 두 번째 입력과 CONV14·CONV20 저장 주소를 layer dump로 추적했습니다.

정수 연산

Requantization 경계 확인

Bias, ReLU bypass, multiplier, shift와 clamp 순서를 layer별로 비교했습니다.

최종 판단

Tensor 차이를 detector 결과로 연결

Mismatch 비율만 줄이는 데 머물지 않고 두 head mAP가 실제로 개선되는지 확인했습니다.
